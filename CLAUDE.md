# CLAUDE.md

Contexto persistente para o Claude Code neste repositório. Este arquivo é o resumo executivo das decisões já tomadas — para o raciocínio completo por trás de cada uma, ver `docs/`. Leia isso inteiro antes de escrever qualquer código.

## O que é este projeto

App pessoal (uso solo) de aprendizado de alemão B2/C1+, construído em cima de três planilhas já curadas pelo usuário (`data/raw/`): gramática (100 regras, fonte *Grammatik aktiv B2-C1*, Cornelsen), fonética (26 pontos, priorizados especificamente para os erros típicos de falante de português, fonte PONS), e uma lista heterogênea de 103 atividades herdadas de uma metodologia própria ("My Way" + um motor semanal C1+ autoral).

O usuário tem TDAH desatento e ansiedade social diagnosticados (LSAS=76), e o design do app segue técnicas comportamentais com evidência específica pra isso — não é um detalhe de UX opcional, é estrutural. Ver `docs/03-fundamentacao-comportamental.md`.

## Decisões já tomadas — não reabrir sem motivo forte

**Infra**: Cloudflare Pages + Workers (Pages Functions) no frontend/backend, D1 (SQLite nativo) como banco. Não usar Postgres — Cloudflare não hospeda Postgres nativamente, Hyperdrive é só proxy pra Postgres externo, e D1 sozinho cobre o volume deste projeto (ordem de 1.500-2.000 exercícios + progresso de 1 usuário). Mídia gerada por TTS vai pro R2 (sem egress, sem OAuth); áudio GRAVADO pelo usuário (pronúncia) vai pro Google Drive, por escolha explícita dele — não mude isso pra R2 sem perguntar.

**Motor de geração de exercícios: multi-provedor via API, decisão revista na Fase 4 (era "100% local", CLAUDE.md antigo).** Decisão original (Fase 0): Ollama 100% local, Mistral Small — motivo registrado abaixo em "Tag exata importa". Revista porque a máquina de geração não sustenta o modelo local com folga de memória (RAM insuficiente pra rodar 22B quantizado sem contenção/lentidão extrema, ver nota histórica). `pipeline/src/deutsch_pipeline/generation/llm_client.py` abstrai o provedor: `chat(model, system, user)` decide por prefixo do nome do modelo (`gemini*`/`gemma*` → Gemini API, `claude*` → Anthropic API, `azure:*` → Azure OpenAI, `hf:*` → Hugging Face Inference Providers, `publicai:*` → Public AI, senão → Ollama local) — nem `pilot.py` nem os 4 gates do harness sabem ou precisam saber qual provedor gerou o texto. Testados nesta sessão: Gemini (`gemini-2.5-flash`, tier gratuito — 20 req/dia, ótima qualidade), Claude API (sem saldo, não testado de fato), Azure OpenAI (sem deployment configurado, não testado), Hugging Face + DeepSeek-V3/Qwen2.5-72B (gratuito, funcionou, confiável), Public AI + EuroLLM-22B (gratuito, especializado em línguas da UE, melhor qualidade pontual mas infra instável — 504 recorrente e formato de saída malformado às vezes, mesmo com backoff exponencial e chamadas menores). **Uso prático recomendado: Gemini como primário (melhor qualidade, mas 20 req/dia no tier grátis — considerar ativar faturamento se o volume da Fase 4 completa precisar de mais), Hugging Face + DeepSeek-V3 como fallback confiável.** Credenciais em `app-root/.env` (gitignored — ver `.env.example` pro formato; `.gitignore` também cobre `client_secret*.json`/`*credentials*.json` depois de um incidente de secret exposto em arquivo não ignorado nesta sessão).

**Harness de validação, corrigido após auditoria e generalizado na Fase 3 (ver `pipeline/src/deutsch_pipeline/validation/harness.py`).** O piloto original media só LanguageTool sobre um campo (`sentence_full`) gerado separadamente do exercício de fato (`prompt` + `accepted_answers`) — as duas strings podiam divergir sem ninguém notar, e o schema de produção (`exercises` em `0001_init.sql`) nem tem coluna pra guardar `sentence_full`. Resultado real por trás do "20/20 auto_ok" original: só 6/20 (30%) reconstruíam corretamente o exercício que o usuário veria. Corrigido com 4 gates, nesta ordem, todos em `validate_batch()`: (1) **estrutural** — o LLM autora só `sentence_full` + `gap_answer` (nunca mais duas strings independentes); o programa corta `prompt_gapped` de dentro de `sentence_full`, o que torna divergência estrutural impossível por construção (`generation/pilot.py`, `build_prompt_gapped`); (2) **aderência à regra** — checagem morfológica via spaCy (`de_core_news_lg`) confirmando que o caso gramatical do token após a lacuna bate com o que o NOME do tópico promete, quando o tópico declara um caso fixo (`validation/rule_adherence.py`, `infer_expected_case` — generalizado por regex de sufixo `"mit Akkusativ/Dativ/Genitiv"`, cobre qualquer um dos 100 tópicos, não só os 4 do piloto); (3) **LanguageTool** (de-DE) sobre `sentence_full`; (4) **respostas alternativas** — descoberto faltando ao demonstrar a Fase 3 contra dados reais: gates 1-3 só validavam a primeira resposta aceita (a usada em `sentence_full`); o modelo inventava variantes erradas (`"auff"`, `"aen"` — erro de digitação, não grafia alternativa legítima como `"ueber"` pra `"über"`) que passavam batido. `check_alternate_answers` reconstrói a frase com CADA resposta aceita e roda LanguageTool em cada uma.

**Resultado real, com os 4 gates**: 4 tópicos de regência (`Wechselpräpositionen`, `Verben, Nomen und Adjektive mit Präpositionen`, e as variantes "...mit Akkusativ"/"...mit Dativ" de "Verben, Adjektive, Nomen und ihre Ergänzungen"), 20 itens, Mistral Small (`mistral-small:22b-instruct-2409-q3_K_M`): **12/20 (60%) `auto_ok`, 0 erro estrutural, 4 `case_mismatch`, 4 `bad_alternate_answer`**. Os 4 erros de caso caem **todos** no tópico "...mit Dativ" (4/5 itens) — o modelo puxa sistematicamente pra idiomas fixos de Akkusativ (`denken an`, `froh über`, `stolz auf`, `dankbar für`) mesmo quando a regra pede Dativ. Os 4 erros de resposta alternativa caem todos no tópico `Wechselpräpositionen` (que sem esse gate parecia 5/5 perfeito). **Decisão do usuário**: aceitar Mistral Small com esse resultado, mas tópicos de regência fixa de Dativ (padrão "verbo/adjetivo + preposição + Dativ") entram na curadoria do `topic_template_map` (Fase 2) marcados para **revisão humana obrigatória**, não geração automática sem checagem — não é um problema do harness, é uma fraqueza específica e reproduzida do modelo nessa categoria. Os 20 exercícios do piloto (validados, `validation_status` correto) estão gravados em `exercises` no D1 local via `ingest/write_exercises.py`, demonstrando o harness ponta a ponta.

**A fraqueza do tópico Dativ é do PADRÃO, não de um modelo específico** — confirmado na Fase 4: DeepSeek-V3, um modelo totalmente diferente do Mistral, errou o mesmo tópico "...mit Dativ" na mesma proporção (4/5 `case_mismatch`, mesmo viés de puxar pra idiomas fixos de Akkusativ). Reforça a decisão de revisão humana obrigatória pra esse padrão de tópico, independente de qual motor gerar.

**Fase 4, primeira fatia: os 18 tópicos mapeados a `GapFillGovernanceEngine` (docs/02, template "Completar lacunas com a regência correta") foram gerados e gravados em `exercises`** via `generation/generate_batch.py` (generaliza `pilot.py`: carrega tópicos do D1 por `topic_template_map` em vez de lista hardcoded, roda os 4 gates, grava com checkpoint por tópico — uma falha no meio do lote não derruba o que já foi gerado/validado/gravado). `generation/model_routing.py` força o modelo mais forte (Gemini) nos padrões historicamente fracos (`Topic.expected_case == "Dat"`, `Funktionsverbgefüge`), deixando o modelo pedido (ex. DeepSeek-V3) livre pros demais — generaliza a regra de curadoria de "revisão humana obrigatória" de nota solta pra política de código.

**Harness ganhou um 5º gate: reparo mecânico de `bad_alternate_answer` (`validation/harness.py`, `find_bad_alternates`).** Antes, uma ÚNICA resposta alternativa ruim (ex. `"auff"`, erro de digitação) descartava o item inteiro, mesmo com `sentence_full`/`gap_answer` limpos em todos os outros gates. Agora `find_bad_alternates` acha TODAS as alternativas ruins (não só a primeira); se sobrar pelo menos `gap_answer` depois de remover as ruins, o item vira `repaired_alternate` (mapeado a `validation_status='auto_ok'`) em vez de `flagged`. Efeito real no lote DeepSeek-V3 (35 itens): 22 `auto_ok` brutos → **28/35 (80%) depois do reparo** (verificado rodando de novo, não só recontado — um relatório colado nesta sessão alegou "94%/33-35", número que não bate com a própria soma por tópico do relatório, que dá 28).

**Workflow de revisão humana fechado (migration `0004_review_workflow.sql`)**: `exercises` ganhou `flag_reason`/`flag_detail` (por que foi flagged, não só que foi) e um 5º `validation_status` (`rejected`, descarta sem apagar a linha — mantém auditoria). `VIEW servable_exercises` (`WHERE validation_status IN ('auto_ok','human_reviewed')`) é o único ponto de leitura que a composição de sessão (Fase 9) deve usar — estrutural, não um lembrete que alguém esquece 5 fases depois. Ciclo: `validation/export_review_queue.py` (D1 → planilha `.xlsx` com dropdown aprovar/corrigir/rejeitar e coluna `motivo` legível) → revisão manual → `validation/import_review_decisions.py` (planilha → D1). Testado ponta a ponta nesta sessão: 2 decisões reais aplicadas (1 `aprovar` — falso positivo do LanguageTool em "infrage stellen" — e 1 `corrigir` — trocou `den`→`dem` num item `case_mismatch` de Dativ), `servable_exercises` foi de 81 pra 83 corretamente. Dois bugs de NaN-truthiness (`not float('nan')` é `False` em Python, então checagens `if not raw` deixavam passar `NaN` pra código que esperava string/None) corrigidos nos dois scripts — afetavam especificamente linhas gravadas antes da migration existir (`flag_reason`/`flag_detail` NULL).

**Estado atual do D1 (18 tópicos, `GapFillGovernanceEngine`)**: 89 exercícios — 81 `auto_ok`, 2 `human_reviewed`, 6 `flagged` (pendentes de revisão: 4 `case_mismatch` no padrão Dativ, mais itens de `Funktionsverbgefüge`/`lt_flagged` reais, não artefato do harness). Ainda faltam os outros 8 templates do Grupo A (nenhum tem código de geração ainda) e os ~82 tópicos restantes da KB não mapeados a `GapFillGovernanceEngine`. **Auditoria de calibração feita**: amostra de 23 itens `auto_ok`/`human_reviewed` (1 por tópico dos 18 + reforço de todos os `repaired_alternate`), revisados um a um contra gramática alemã real (regência, caso, idiomatismo). **22/23 corretos** — o harness de geração/validação não mostrou falso-negativo nesta amostra. O único problema achado não veio da geração: era **dado corrompido pelo próprio workflow de revisão humana**, testado nesta sessão — item 85 (`Verben...mit Dativ`, já `case_mismatch`) tinha `accepted_answers` literalmente `["nan"]` porque uma célula `accepted_answers_corrigido` vazia na planilha de teste virou `NaN` do pandas, que é *truthy* em Python puro (mesma classe de bug de `export_review_queue.py`, agora uma 3ª ocorrência em `import_review_decisions.py`, corrigida com um helper `_clean_cell` compartilhado). Item 85 marcado `rejected` (não tem correção válida trocando só o caso — "sich freuen über" é regência fixa de Akkusativo, sem variante Dativ). **Estado servível atual: 82** (era 83 antes do reject).

**Segundo template do Grupo A: `FillBlankEngine` (docs/05 item 17), generalização direta do `GapFillGovernanceEngine`.** O próprio docs/05 já apontava isso: "pode reusar a mesma engine..., diferindo só na fonte da regra" — a lacuna aqui testa qualquer elemento gramatical (tempo verbal, declinação, conector, sufixo de formação de palavra), não especificamente regência de caso/preposição. Refatoração pra viabilizar: `generation/pilot.py` `generate_for_topic` agora recebe `system_prompt`/`template_name`/`user_prompt_builder` como parâmetros em vez de importar um módulo fixo; `generation/generate_batch.py` ganhou `--engine` com um registro `ENGINE_PROMPTS` (hoje: `GapFillGovernanceEngine` → `prompts.py`, `FillBlankEngine` → `prompts_fillblank.py`) — todo o resto (harness de 5 gates, checkpoint por tópico, `model_routing.py`) é 100% reaproveitado sem mudança, nenhuma lógica nova por template. 55 tópicos mapeados a `FillBlankEngine` no `topic_template_map` (categorias 6-12, 15-17: tempos verbais, modais, artigos/pronomes, adjetivos, discurso indireto, Nebensätze, palavras especiais, formação de palavras, numerais, partículas).

**`FillBlankEngine` completo: os 55 tópicos mapeados foram gerados** (primeira fatia de 5 tópicos com Gemini, 25/25 `auto_ok`; depois 15 tópicos com Gemini até estourar cota; os 36 tópicos restantes com `hf:deepseek-ai/DeepSeek-V3`, mais `Funktionsverbgefüge 1/2` forçados pro Gemini via `model_routing.py`). **Estado final no D1: 281 exercícios em 55/55 tópicos, 277 servíveis (98,6%)** — 247 `auto_ok` brutos + 30 `repaired_alternate` (gate 5, resposta alternativa ruim removida mecanicamente), só 4 `flagged` reais (`lt_flagged`: 1 em `Indefinitpronomen für Menschen`, 3 em `Funktionsverbgefüge 1` — este último já é o padrão historicamente fraco, mesmo forçando o modelo mais forte).

Durante a rodada com Gemini, 4 tópicos (`Gebrauch von Zeiten der Vergangenheit`, `Vermutung und Zukunft mit dem Futur`, `Überblick über die Zeiten im Deutschen`, `Artikelgebrauch`) tiveram `structural_mismatch` alto (até 4/5) por dois motivos de fundo, não falha pontual do modelo: (1) construção verbal partida (Perfekt/Plusquamperfekt/Futur em oração PRINCIPAL — auxiliar na posição 2, particípio/infinitivo no final, com texto no meio — nunca é substring contígua, então `build_prompt_gapped` sempre falhava); (2) regra sobre AUSÊNCIA de artigo (`gap_answer` não pode ser string vazia). `prompts_fillblank.py` ganhou uma seção "ATENÇÃO" no `SYSTEM_PROMPT` instruindo a preferir oração SUBORDINADA (cluster verbal fica junto no final) ou delimitar a lacuna só na parte que varia, e a ilustrar o CONTRASTE em vez do caso de ausência. Reprocessados os 3 tópicos que sobraram fora do lote principal (`Gebrauch von Zeiten der Vergangenheit`, `Überblick über die Zeiten im Deutschen`, `Artikelgebrauch`) com o prompt corrigido: **15/15 `auto_ok`**, confirma que o problema era o prompt, não o modelo.

**Auditoria de calibração do `FillBlankEngine`**: amostra de 81 itens (30 `repaired_alternate` completos + 51 `auto_ok`, 1 por tópico) revisados manualmente contra gramática alemã real. **79/81 corretos (~97,5%)**, 2 erros reais achados e corrigidos direto no D1 (`validation_status='human_reviewed'`, mesmo padrão do workflow de revisão): item 186 (`Indefinitpronomen für Menschen`) aceitava `"Jemandem"`/`"Jemanden"` (dativo/acusativo) numa lacuna de SUJEITO (nominativo) — só `"Jemand"` é válido ali, corrigido pra manter só essa; item 214 (`Indirekte Rede und Konjunktiv 1`) aceitava `"wäre"` (singular) pra um sujeito plural (`die Ergebnisse`), sem concordância — corrigido pra manter só `"wären"`. Os dois são falso-negativo do LanguageTool pra concordância de caso/número em posições que o checker não pega bem isoladamente (pronome indefinido como sujeito, subjuntivo com sujeito plural) — mesma classe de limitação já registrada na auditoria do `GapFillGovernanceEngine` (22/23), não um problema novo.

**Terceiro template do Grupo A: `UnscrambleEngine` (docs/05 item 19) — sem lacuna, reordenar tokens.** Contrato diferente dos dois anteriores: o LLM autora só `sentence_full` (frase inteira correta, nível B2/C1, aplicando a regra de ordem do tópico — V2, TeKaMoLo, posição de Nebensatz, pronome relativo etc.), sem `gap_answer`. O programa tokeniza por espaço em branco e embaralha (`generation/prompts_unscramble.py`, `tokenize`/`shuffle_tokens` — reembaralha até garantir ordem diferente da original, pra não entregar quebra-cabeça já resolvido); `exercises.prompt` guarda o array JSON dos tokens embaralhados (não mais uma string com "___") e `accepted_answers` guarda `[sentence_full]`. Pra reaproveitar os 5 gates do harness (`validation/harness.py`) sem alterá-los, `gap_answer` é setado como a frase INTEIRA — `check_case_adherence` cai em "n/a" (nenhum dos 21 tópicos declara caso fixo no nome) e `find_bad_alternates` não dispara já que o único item de `accepted_answers` é igual a `gap_answer` (nenhuma alternativa extra ainda). Viabilizado generalizando `generation/pilot.py`: `generate_for_topic` ganhou parâmetro `exercise_field_builder` (default `build_exercise_fields_gapfill`, que é o comportamento antigo extraído sem mudança) — `generate_batch.py` ganhou um registro `EXERCISE_FIELD_BUILDERS` paralelo ao `ENGINE_PROMPTS` pra templates fora do contrato de lacuna escolherem o builder certo.

**Resultado do `UnscrambleEngine`: 105 exercícios em 21/21 tópicos, 104 servíveis** (todos `auto_ok`/`human_reviewed` pelos 5 gates do harness, DeepSeek-V3). Auditoria manual em 37 itens (20 do piloto + 17 da amostra do lote completo, 1 por tópico): **36/37 corretos**. 1 erro real achado e corrigido — item 381 (`Position der Angaben im Satz`) usava `"Er hat ... mit dem Auto zur Arbeit gefahren"`; `fahren` intransitivo de movimento com `mit + meio de transporte` exige o auxiliar `sein` no Perfekt, não `haben` — corrigido pra `"Er ist ..."` direto no D1 (token trocado no `prompt` embaralhado + `accepted_answers`, `validation_status='human_reviewed'`). Mesma classe de limitação já registrada nas auditorias anteriores: LanguageTool não pega de forma confiável seleção de auxiliar (`haben`/`sein`) quando há vários modificadores entre o auxiliar e o particípio.

**Quarto template do Grupo A: `StructuralTransformEngine` (docs/05 item 21) — par de frases A→B, o risco estrutural mais próximo do bug original da Fase 0.** Diferente dos três anteriores, aqui o LLM NECESSARIAMENTE autora duas strings relacionadas (`sentence_a`, forma de partida lida pelo usuário; `sentence_b`, a transformação que ele precisa produzir — Konjunktiv II, Passiv, discurso indireto, Nominalisierung etc.). Mitigação sem duplicar `validation/harness.py`: as duas frases são concatenadas num único `sentence_full` (`generation/prompts_structuraltransform.py`, `_as_lt_sentence` capitaliza e garante pontuação final em cada metade antes de concatenar — sem isso o LanguageTool trata as duas como UMA frase contínua e erra a checagem de maiúscula) — o LanguageTool roda sobre o texto inteiro, pegando erro em QUALQUER uma das duas metades, sem mudar o harness. `gap_answer = sentence_b` reaproveita os gates 4/5 (alternativas) sem novo código.

**O que o harness NÃO verifica (e não dava pra saber sem testar): se `sentence_b` é de fato a transformação certa, não só uma frase gramatical qualquer.** Auditoria manual do piloto (25 itens, 5 tópicos diversos) achou um padrão reproduzido: 2/5 itens de `Passiv in allen Zeiten` trocavam o TEMPO verbal entre A e B (ex. Perfekt ativo → Präteritum passivo, cada frase gramatical isoladamente, mas não é a mesma transformação) — corrigido com instrução explícita no `SYSTEM_PROMPT` (tempo tem que bater dos dois lados, só a voz muda); reprocessado, 0/4 `auto_ok` repetiu o problema. Rodando o lote completo (17 tópicos restantes) apareceram mais dois problemas reais: (1) o mesmo descompasso de tempo reapareceu em `Passivsätze ohne Subjekt`, tópico da mesma família mas não citado pelo nome na instrução original — generalizada a instrução pra cobrir qualquer mudança-só-de-voz; (2) **3 tópicos inteiros (`Passiv mit Modalverben in allen Zeiten`, `Indirekte Rede – Vergangenheit`, `Infinitiv mit und ohne zu`) vieram com `sentence_a == sentence_b` em TODOS os 5 itens** — a regra desses tópicos descreve só a forma-alvo sem mencionar uma forma de partida explícita, e o LLM, sem instrução clara, devolveu a mesma frase duas vezes (exercício sem propósito, nada pra transformar). Corrigido com gate MECÂNICO (não só prompt) em `build_exercise_fields_structuraltransform`: `sentence_a.strip().lower() == sentence_b.strip().lower()` vira `structural_mismatch` sempre, mais instrução explícita de como inventar a forma de partida (Aktiv+modal pra Passiv-com-modal; discurso direto entre aspas pra Indirekte Rede). Os 15 itens idênticos já gravados como `auto_ok` foram marcados `rejected`.

**Curadoria de `topic_template_map` revisada**: `Infinitiv mit und ohne zu` (tópico 67) removido do `StructuralTransformEngine` — é fundamentalmente um tópico de RECONHECIMENTO (quais verbos exigem "zu"), não de transformação, e já tem cobertura boa via `FillBlankEngine`/`UnscrambleEngine` (ambos 5/5 quando gerados). `Wann ist Passiv möglich, wann nicht?` (tópico 19) também não serve pro formato A→B deste engine pela mesma razão (é sobre reconhecer verbos que NÃO admitem passivo, ex. "besitzen") — mantido mapeado por ora (nenhum template atual serve melhor), mas marcado pra recuradoria futura, não pra geração automática.

**Resultado final do `StructuralTransformEngine`: 101 exercícios servíveis em 20/21 tópicos mapeados** (só o tópico 19, doc acima, ficou sem conteúdo servível — 5/5 `structural_mismatch` corretamente, não é bug). Também achou e corrigiu um falso positivo do LanguageTool em `Links- und Rechtsattribute` (tópico 83): os pares ali são SINTAGMAS nominais, não frases completas (ex. "die von uns gestern besichtigte Wohnung"), o que disparava `UPPERCASE_SENTENCE_START` (frase minúscula) — resolvido pela mesma função `_as_lt_sentence` (capitaliza + garante pontuação só na cópia usada pelo gate, nunca no que o usuário vê).

**Quinto template do Grupo A: `RegisterReformulationEngine` (docs/05 item 10) — só 2 tópicos, ambos redundantes com outros templates.** `Nominalisierung` (82) e `Nominalisierende Suffixe` (89) já tinham cobertura em `StructuralTransformEngine`/`FillBlankEngine` — aqui é uma modalidade de exercício diferente sobre o mesmo conteúdo (projeto varia formato de propósito). Mecanismo de correção é HÍBRIDO por design do docs/05 (checagem determinística de padrão + nota de fluência via LLM leve) e a parte de fluência é inerentemente tempo-real (avalia a resposta que o usuário deu, não uma resposta fixa) — isso é Fase 9 (frontend/Worker), fora do escopo desta fase; `generation/prompts_registerreformulation.py` reexporta `build_exercise_fields_structuraltransform` sem modificação (mesmo contrato de par sentence_a/sentence_b), só com `TEMPLATE_NAME` próprio pra não colidir no registro reverso de `generate_batch.py`.

**Achado real: 8/10 itens do primeiro lote (Gemini) e depois 3/4 de uma segunda tentativa (EuroLLM) acrescentavam uma oração de CONSEQUÊNCIA que não estava na frase original** (ex.: "Die Polizei untersucht den Vorfall gründlich." virou "Durch die gründliche Untersuchung des Vorfalls erwartet man baldige Aufklärung." — "espera-se esclarecimento em breve" é conteúdo novo). Causa raiz identificada: o próprio `exemplo` curado do tópico `Nominalisierung` na planilha original ("Durch die konsequente Nutzung von Nomen entsteht sprachliche Verdichtung") já tem a estrutura "Durch X entsteht Y", e o modelo imita essa ESTRUTURA (não só o registro) mesmo depois de instrução explícita com par certo/errado no `SYSTEM_PROMPT`. Reproduzido em DOIS modelos diferentes (Gemini e EuroLLM-22B) — padrão do tópico, não do modelo, mesma classe de achado do caso Dativ da Fase 0. `Nominalisierende Suffixe` (89) não tem esse problema (exemplo curado não tem a mesma estrutura). **Resolvido depois com HF Pro + DeepSeek-R1**: usuário assinou Hugging Face Pro nesta sessão (20x mais crédito mensal de Inference Providers) e pediu pra testar se um modelo de raciocínio resolvia o viés de conteúdo que Gemini (2/10 fiéis) e EuroLLM (2/9 fiéis em duas tentativas) não resolveram mesmo com instrução explícita (par certo/errado no prompt). **`hf:deepseek-ai/DeepSeek-R1` acertou 4/4 na mesma tentativa** — zero deriva de conteúdo, todos usando construção com verbo-suporte (durchführen/betreiben/vornehmen) exatamente como o exemplo "CERTO" do prompt pedia. **Geração é sempre constrained pela KB, nunca "LLM inventa a regra"**: todo prompt de geração usa a regra + exemplo já curados nas planilhas como few-shot. O programa decide a forma gramatical correta a partir da KB; o LLM só varia vocabulário/contexto/fluência.

**Fonética e fala com comparação de fonema a fonema (aprovado — ver `docs/08-fonetica-e-fala.md`)**: pipeline 100% local pra responder "o usuário pronunciou certo?" — `phonemizer`/`espeak-ng` gera o IPA-alvo do texto de referência; um reconhecedor de fones local (`wav2vec2-lv-60-espeak-cv-ft` ou `allosaurus`, escolha por piloto empírico como na Fase 0, não por documentação) reconhece o que foi dito; um diff fonema a fonema entre os dois mostra acerto/erro em IPA. Azure Pronunciation Assessment/SpeechAce ficam só como benchmark de validação pontual, não como padrão — quebrariam o princípio de motor 100% local. Duas engines novas em `docs/05` (linhas 114-115): `ReadAloudEngine` (vê o texto, grava lendo, ouve/regrava à vontade antes de submeter, feedback com fonemas errados destacados, só então ouve o áudio-gabarito — nome já estabelecido na literatura de CAPT, não é o Shadowing por ser texto-primeiro em vez de áudio-primeiro) e `SpokenGapFillEngine` (variante em voz do `GapFillGovernanceEngine`, item 9 — combina checagem lexical via STT/`accepted_answers` com a checagem de pronúncia, mostradas **separadas**, nunca num score único). Áudio-alvo desses dois vem do TTS (Piper) da mesma frase já gerada pela KB — não é um problema de sourcing novo, é o mesmo mecanismo que já alimenta o `DictationEngine` (item 28); Forvo (API de pronúncia por palavra) fica como enriquecimento opcional só pro caso de vocabulário isolado (linha 116). `ShadowingEngine` (item 2) mantém "sem correção automática" como já estava documentado — a variante base fica igual, áudio-only (nunca vídeo, mais simples e consistente entre fonte de vídeo e TTS). Uma segunda opção com correção foi adicionada lado a lado, não em substituição: "Shadowing com correção" (linha 117, mesma mecânica do item 2 + diff fonético pós-gravação) e "Shadowing de vocabulário isolado" (linha 116, mesma ideia numa palavra em vez de frase) já nascem na variante corrigida — usuário escolhe qual praticar conforme a sessão. Granularidade "vocabulário isolado" existe nas duas famílias agora: `ShadowingEngine` (linha 116, áudio-primeiro) e `ReadAloudEngine` (linha 118, texto-primeiro, mesmo par frase/palavra que já existia entre os itens 114 e 116) — IPA-alvo dessas duas vem de `lexicon.ipa` (já curado via Wiktionary) quando a palavra já estiver no léxico, com `phonemizer` como fallback só pra palavra nova. Contrastes de Alta prioridade da planilha de fonética (duração vocálica, Umlaut) que um reconhecedor de fones generalista tende a não pegar bem ganham reforço opcional de fase 2 com `Parselmouth` (medida direta de duração/formantes). Roleplay de voz do Grupo D usa um loop simples turn-based (grava → `faster-whisper` local → Ollama → Piper → toca) — **não CrewAI** (framework pra múltiplos agentes autônomos delegando tarefa, não se aplica a uma persona única conversando com o usuário) **nem Pipecat por enquanto** (framework de voice agent real, mas full-duplex/baixa-latência é mais do que o Grupo D precisa — mesmo padrão de "não é infraestrutura de dia 1" já usado pro léxico). Schema: tabela `phoneme_scores` e campo `source_type` em `exercises`, em `app/migrations/0001_init.sql`.

## Especificação de engines por exercício

`docs/05-engines-por-exercicio.xlsx` tem 118 atividades — as 103 da planilha original, mais as 10 do bloco de leitura/notícia, mais as 5 de fonética/fala (`ReadAloudEngine`, `SpokenGapFillEngine`, shadowing de vocabulário isolado, shadowing com correção, Read Aloud de vocabulário isolado) — cada uma tratada como unidade de engine/módulo: nome de classe proposto, mecanismo de correção, stack, interação do usuário e apresentação visual. É a referência pra nomear e implementar cada módulo em `app/src/lib/`. Consultar antes de criar uma engine nova — muitos itens já reusam a mesma classe (ex. `VideoTaskEngine` cobre dublagem, legendagem, interpretação e citação com um parâmetro de subtipo).

## Workflow de trabalho — como avançar

Trabalhar em fatias pequenas e verificáveis, seguindo as fases abaixo na ordem. **Depois de cada fase, e de cada sub-tarefa dentro dela, parar e reportar — não seguir automaticamente pra próxima sem o usuário confirmar.** Cada fase precisa terminar em algo que dá pra rodar e olhar (comando de CLI com output legível, ou preview local via `wrangler dev`/`wrangler pages dev`), nunca só código sem demonstração.

0. Piloto do motor de geração — comparar candidatos num único tópico real, validar com LanguageTool, usuário escolhe.
1. Ingestão — script que lê as 3 planilhas e popula `content_topics`/`phonetic_points` no D1.
2. Curadoria `topic_template_map` — mapear quais templates do Grupo A se aplicam a quais tópicos (trabalho humano assistido, não 100% automático).
3. Harness de validação — checagem determinística + integração LanguageTool.
4. Pipeline de geração em lote pro Grupo A.
5. Bloco de leitura/notícia — gerar texto original (citando DW/ZDF/Nachrichtenleicht como inspiração), popular `reading_blocks`/`reading_block_items`, implementar as 10 engines de `docs/05` linhas 104-113.
6. Sourcing e transcrição de vídeo (Grupo E) — yt-dlp contra a lista de canais/playlists permitidos (DW Video-Thema principal), popular `video_clips`/`video_transcript_segments`, implementar as variantes de `VideoTaskEngine` (legendar/citar) e do `DictationEngine` que dependem de transcrição real — ver `docs/07-sourcing-de-video.md`.
7. TTS em lote (Piper local ou API barata).
8. Fonética e fala — piloto empírico (5-10 amostras gravadas cobrindo os pontos de Alta prioridade) comparando `wav2vec2-espeak` vs. `allosaurus`, contra benchmark pontual da Azure; depois de escolher, implementar `ReadAloudEngine`/`SpokenGapFillEngine` e o loop de voz turn-based do Grupo D — ver `docs/08-fonetica-e-fala.md`.
9. Frontend mínimo consumindo o D1 (sessão + composição intercalada + FSRS).
10. Motor semanal (Grupo B) com captura de `session_plans`.
11. Grupo D (roleplay texto/voz).
12. Amostragem humana e ajuste fino.

## O que NÃO fazer

- Não gerar exercícios pro Grupo C sem pedido explícito e nomeado.
- Não misturar validação de exposição com correção gramatical no mesmo retorno.
- Não propor Postgres/Hyperdrive — decisão já fechada em favor de D1.
- Não pré-popular o léxico com lista de frequência de nível básico.
- Não avançar de fase sem o usuário ter revisado e aprovado a fase anterior.
- Não copiar/raspar texto literal de DW, ZDF ou Nachrichtenleicht para os blocos de leitura — gerar texto original citando a fonte como inspiração factual.
- Não mostrar transcrição de vídeo/áudio ao usuário como texto pra ler antes da tentativa — só como gabarito pós-tentativa (mesma regra do bloco de leitura).
- Não baixar/re-hospedar o arquivo de vídeo em si — só a transcrição (D1); apresentação continua via `iframe` do YouTube.
- Não usar a YouTube Data API oficial pra baixar legenda de vídeo de terceiro — ela só serve vídeo do próprio dono do canal. Usar `yt-dlp`.
- Não misturar checagem de palavra certa (léxico/gramática) com qualidade de pronúncia no mesmo score — mostrar como feedback separado (mesmo princípio de `showed_up`/`correction_json`).
- Não usar CrewAI (ou framework de múltiplos agentes) pro roleplay de voz do Grupo D — é uma persona única conversando com o usuário, não uma equipe de agentes delegando tarefa.
- Não remover a variante sem correção do `ShadowingEngine` (item 2) — ela continua existindo como está (foco em prosódia, sem diff automático); a variante com correção (item 117) é uma opção adicional lado a lado, nunca uma substituição.
